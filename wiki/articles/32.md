## [1. Reconfigure input](scenario:RECONFIGUREINPUT)

### **When is it used**  
Click **RECONFIGURE** on the Project Setup page.

### **Why**  
Automatically switch your LLM-usage pipelines to the right data sources, storage, formats, engines, and dependencies based on your project variables.

### **What it does**  

1. **Read variables**  
   `logs_origin`, `logs_connection`, `logs_partitioning_*`, `managed_dataset_connection`, `visual_recipes_engine`, etc.

2. **Select input**  
   Picks the raw-logs dataset (`cloud` / `event_server` / `log4j`) and the “to dashboard” table.

3. **Rewire recipe**  
   Points `compute_llm_logs_prep` at the chosen raw-logs dataset.

4. **Update connections**  
   - **Raw logs**: set `connection` & `type`  
   - **Managed DS**: switch to filesystem+CSV _or_ cloud+Parquet (Snappy/Hive)

5. **Partitioning**  
   Clear then (re-)apply time partitions if enabled, using your period & pattern.

6. **Switch compute engine**  
   Run visual recipes on your chosen engine (e.g. Spark) with Spark configs.

7. **Set recipe deps**  
   - If partitioned: “equals” on each partition  
   - For the final “complete” recipe: wait for **all_available** partitions

## [2. Setup and Build](scenario:SETUP)   

### **When is it used:**  
Click **APPLY AND BUILD** on the Project Setup page.

### **Why**  
Automatically inject your time-partition build range, then kick off the full pipeline.

### **What it does**  
1. **Load variables**  
   - `logs_partitioning_build_range`  
   - `logs_partitioning_activated`  
2. **Patch the “Build flow” scenario**  
   - If partitioning is on: set its first step’s `partitionsSpec` to your build range  
   - Otherwise clear `partitionsSpec`  
3. **Save** the updated scenario settings  
4. **Trigger** Scenario [3. Build flow](scenario:BUILDFLOW)

## [3. Build flow](scenario:BUILDFLOW)

### **When:**  
Triggered by [2. Setup and Build](scenario:SETUP)

### **Why:**  
– Materialize your partitioned flow-zone tables  
– Then run the final aggregation recipe

### **What happens:**  
1. **Build partitioned datasets**  
   - **Item:** `logs_llm_usage_prepared_by_Project`  
   - **Partitions:** uses the build range set in Step 2  
   - **Mode:** Build upstream (force rebuild)  
   - **Deps:** force-build all upstream  
   - **Sync:** Hive metastore  
2. **Run final recipe**  
   - **Item:** `logs_llm_usage_prepared_by_Project_complete`  
   - **Partitions:** N/A  
   - **Mode:** Build upstream  
   - **Deps:** build required dependencies  

### UI Steps

1. **Build** step: choose your main dataset + partition spec, force-build upstream  
2. **Build** step: choose the “_complete” dataset, build required dependencies

## [1.1. Reconfigure Continuous Flow Build](scenario:11RECONFIGURECONTINUOUSFLOWBUILD)

### **When is it used**  
This scenario is triggered when you update the project settings on the **Project Setup page** in your "LLM Cost Guard" project, specifically when settings related to continuous builds (e.g., `activate_continuous_build`, `logs_origin`, or partitioning options) are modified. It ensures the continuous build scenario adapts to your configuration without requiring manual adjustments.

### **Why**  
The purpose of this scenario is to dynamically configure the **[4. Continuous Flow Build](scenario:4CONTINUOUSFLOWBUILD)** scenario so that it:
- Activates or deactivates based on your preferences.
- Monitors the correct raw logs dataset (e.g., from event server, cloud, or log4j) for new data.
- Adjusts for time-based partitioning (if enabled) to process data continuously without gaps.

This keeps your LLM usage tracking pipeline flexible and responsive to changes in data sources or partitioning needs, minimizing manual intervention.

### **What it does**  
This script modifies the settings of the [4. Continuous flow build](scenario:4CONTINUOUSFLOWBUILD) scenario based on project variables. Here’s a step-by-step explanation:

1. **Load Project Variables**  
   The script reads the following variables from your project settings:
   - `logs_origin`: Specifies the source of raw logs (`event_server`, `cloud`, or `log4j`).
   - `activate_continuous_build`: A boolean (`True` or `False`) indicating whether continuous builds should run.
   - `logs_partitioning_activated`: A boolean showing if time-based partitioning is enabled.
   - `logs_partitioning_period`: Defines the partitioning period (e.g., `"HOUR"`, `"DAY"`, `"MONTH"`, or `"YEAR"`).

2. **Access the Continuous Build Scenario**  
   It retrieves the [4. Continuous flow build](scenario:4CONTINUOUSFLOWBUILD) scenario and its settings using the Dataiku API.

3. **Activate or Deactivate the Scenario**  
   The scenario’s `active` status is set to the value of `activate_continuous_build`. If `True`, the continuous build process runs; if `False`, it’s disabled.

4. **Configure Triggers and Build Steps**  
   The configuration depends on whether partitioning is enabled (`logs_partitioning_activated`).

   #### **If Partitioning is Enabled**  
   - **Map Partition Periods**:  
     A dictionary maps your chosen period to a "current" partition specification
   - **Set Up Triggers**:  
     The script configures the scenario’s trigger to watch for changes in the raw logs dataset, using the appropriate partition (e.g., `CURRENT_DAY`). Depending on `logs_origin`
   - **Update Build Steps**:  
     The scenario builds the `logs_llm_usage_prepared_by_Project` dataset for **both the current and previous partition** (e.g., `CURRENT_DAY` and `PREVIOUS_DAY`). This ensures no data is missed if the "current" period shifts between builds.

   #### **If Partitioning is Disabled**  
   - **Set Up Triggers**:  
     The trigger watches the entire raw logs dataset (no partitioning) based on `logs_origin`
   - **Update Build Steps**:  
     The scenario builds the entire `logs_llm_usage_prepared_by_Project` dataset without partitioning.

5. **Save the Settings**  
   The updated scenario settings are saved, applying your configuration to the continuous build process.

[4. Continuous flow build](scenario:4CONTINUOUSFLOWBUILD)

### **When is it used**  
Auto-triggered according to if 
- you have ticked **Activate continuous build** on the Project Setup page
- ran **APPLY** 
- your source log dataset has changed (checks for changes each 4 hours by default)

### **What it does**  
Builds the whole flow with the new data that has been added in the source logs

That’s all—your LLM-usage tables are built and the final recipe runs to completion.
